It deliberately excludes the CI steps marked `continue-on-error` (typecheck via `cd apps/main && bun run check`, `format:check`, the final `build`) — those are non-blocking/known-rot, not part of the enforced gate.

- Integration tests: `make integration` (sequential) or `bun test integration/`
- Single test: `bun test path/to/test.test.ts`
- Coverage: `make coverage` then `make coverage-stats`

## Code Style & Architecture

- Naming: snake_case (variables), camelCase (functions), PascalCase (classes/types)
- Use one-word names when possible: `getProjects()` -> `projects.get()`
- Prefer nested objects over complex function names in interfaces
- Pure functions & composition over classes/inheritance
- Avoid if/else - use early returns instead
- Avoid try/catch - use errors as values with union types
- Max 5 layers indentation - refactor deeper nesting into smaller functions
- Builder pattern over large constructors (with sane defaults)
- Import using aliases when beneficial
- No comments except for complex business logic

3. **Plan**: Layout implementation strategy based on interfaces & tests

## Database Type Architecture

- Single `Database` type defined in `packages/schema/src/database/types.ts`
- Uses `BaseSQLiteDatabase<"async", unknown, FullSchema>` -- works for both Bun SQLite (dev/test) and D1 (production)
- `FullSchema` merges devpad + blog + media schemas in `packages/schema/src/database/full-schema.ts`
- Only TWO casts exist in the entire codebase, both at construction boundaries:
  - `createD1Database` in `d1.ts` -- `as unknown as Database`
  - `createBunDatabase` in `bun.ts` -- `as unknown as Database` (sync-to-async bridge)
- All service functions in `packages/core/src/services/` take `db: Database`
- `drizzle-orm` is deduplicated via root `package.json` overrides
- Blog's `DrizzleDB` and Media's `Database` are both re-exports of the unified `Database` type

## Pipelines module

The `packages/pipelines/` Worker is a separate Cloudflare Worker (not part of `devpad-unified`), exporting a `PipelineRunDO` Durable Object and a Hono REST API. The Worker holds **no upstream API keys** — all third-party traffic crosses the security boundary into `~/dev/vault` (separate repo, **same Cloudflare account** — the boundary is logical, enforced by the service-binding RPC contract and the secrets-store secret name `ANTHROPIC_API_KEY`). The orchestrator hosts the grants registry (`pipeline_grant` table) and exposes a `grants.check(caller, scope)` RPC that vault calls.

### Platform singleton model (Phase 12)

Platform services (`pulse`, `vault`, `devpad-pipelines`) are deployed ONCE — they're control plane (observability backplane, secret broker, orchestrator), not workloads-under-test. Their staging Workers were decommissioned in Phase 12. Stage scoping is enforced at:

- **vault**: `caller.environment` on the RPC identity arg (Phase 7) — `grants.check(...)` matches against this literal.
- **pulse**: `environment` tag on each event body — events from staging and production callers all land in `pulse-db-production` but are queryable by tag.

Workload Workers (scaffolded packages such as `anthropic-search`, `anthropic-summarize`) **do** keep the staging+production split. Only the upstream platform service bindings collapse to singletons (`vault`, `pulse-api` — renamed from `vault-production` / `pulse-api-production` in Phase 13.C).

### Deploy gotchas (carry-over from vault)

- **Drop `"rpc"` from `compatibilityFlags`.** It became a default 2024-04-03 and Cloudflare rejects the deploy if specified explicitly.
- **Use the Alchemy OAuth profile `default`** (configured via `bunx alchemy configure`), not the limited `CLOUDFLARE_API_TOKEN` in `devpad/.env`. That env var is commented out for this reason.
- **Account is capped at one `default_secrets_store`.** When binding a `Secret`, use `SecretsStore("<id>", { name: "default_secrets_store", adopt: true })`. The pipelines Worker has no Secrets bound today, so this doesn't apply yet — but vault does, and any future pipelines secrets must adopt the same store. Bound secrets are scoped by name; the boundary is preserved at the secret level.
- **`ALCHEMY_PASSWORD` (in devpad/.env) is only required when Alchemy persists Secret values in state.** Pipelines doesn't bind any secrets currently. Generate with `openssl rand -hex 32` and keep stable across deploys if a future deploy adds secrets.
- **Tokens in test logs**: when an agent runs a test call that uses a bearer token (CF API, devpad PIPELINES_TOKEN, pulse ingest key, etc.), the full token should NEVER appear in command output that gets captured by the agent's transcript. Use parameter substitution + redact in echoed commands: e.g. `echo "TOKEN=${TOKEN:0:6}…${TOKEN: -4}"` not `echo $TOKEN`. This prevents tokens from being exposed in the orchestrator-phase outputs and permanent logs. If captured, treat as compromised and rotate.

### Cloudflare API integration gotchas (Phase 6)

The `CloudflareProvider` lives in `packages/pipeline-fakes/src/cloudflare/` with an HTTP-backed implementation (`http.ts`) hitting the Cloudflare REST API directly. Subtleties surfaced during the Phase 6 conversion to the live account:

- **Workers Versions API uses `multipart/form-data`, not JSON.** A version upload is a multipart body with a `metadata` part (`Content-Type: application/json` for the script metadata) plus one or more file parts for the script + any modules. Posting JSON returns a 400 immediately. The provider builds the body via `FormData` + a `Blob` for the script contents — see `cf-api-multipart.test.ts` for the exact wire shape.
- **Only `workers/message`, `workers/tag`, and `workers/alias` are valid annotation keys** when uploading a version. Other keys (e.g. `version_set_id`, `git_sha`) return Cloudflare error 10021 ("annotation key not recognised") and the version doesn't upload. If you need to thread a custom identifier through, encode it into `workers/tag` (it's free-form) and parse client-side.
- **Service binding `entrypoint` only resolves named class exports.** When binding to a `WorkerEntrypoint` subclass (e.g. `PipelinesGrantsEndpoint`, `AnthropicVault`), you MUST set `entrypoint: "ClassName"` in the binding spec — without it, Cloudflare binds to the default export and any RPC method call returns "The RPC receiver does not implement the method '...'". Alchemy's `WorkerRef` factory drops the `entrypoint` field; pass `{ type: "service", service: "...", __entrypoint__: "ClassName" }` directly until the public API exposes it.
- **Use `--external cloudflare:*` when bundling without wrangler.** The `cloudflare:workers` and `cloudflare:sockets` imports are resolved by the Workers runtime, not by your bundler. Bun/esbuild treat them as missing modules unless explicitly externalised. `--packages=external` is the wrong knob here — it excludes node_modules, not virtual imports.
- **`DurableObjectId.toString()` returns hex, not the original name.** If you constructed the id via `namespace.idFromName("run_abc")` and need the original `"run_abc"` back, read `id.name` (only set when the id originated from `idFromName`). Round-tripping through `toString()` loses it. The DO router relies on this for the `/runs/:id` route.
- **CLI spinners are silent in non-TTY environments (CI logs).** `ora` and similar libraries detect `process.stdout.isTTY` and degrade to no-ops. Always emit a parallel `console.error(message)` so CI logs surface the same status updates.
- **Pin Node 22 in CI for wrangler v4.** Wrangler v4 requires Node ≥ 22.16; older runners install Node 18 by default and the deploy fails on a `module not found` for `node:worker_threads`. The pipelines workflow sets `actions/setup-node@v4` with `node-version: 22.16.0` explicitly.

### Cross-repo service-binding wiring (two-pass deploy)

Vault and pipelines bind to each other:

- vault → pipelines: `GRANTS` (RPC entrypoint `PipelinesGrantsEndpoint`), `PULSE` service binding
- pipelines → vault: `ANTHROPIC` (RPC entrypoint `AnthropicVault`), `PULSE` service binding

Post-Phase 12/13.C there is only one pulse Worker on this account, `pulse-api` (renamed from `pulse-api-production` in Phase 13.C; the `pulse-api-staging` variant was decommissioned in Phase 12). All callers — workloads at either stage and platform services — bind to `pulse-api` and tag events with their own `environment`.

First-time setup uses a two-pass deploy to break the circular dependency: deploy vault without the bindings (vault's `infra.ts` gates `GRANTS` + `PULSE` behind `WIRE_GRANTS_BINDING=true`), deploy pipelines normally (its bindings to vault resolve at upload time since vault already exists), then re-deploy vault with `WIRE_GRANTS_BINDING=true`. Subsequent deploys of either repo don't need the gate — both Workers exist.

### Cross-repo invariants (Phase 7)

- **CF service bindings do NOT propagate `vars` from caller to callee.** When Worker A (with `CALLER_PACKAGE=foo`, `CALLER_ENV=staging` in its env) calls Worker B via a service binding, Worker B's `env` contains its OWN vars, not A's. Identity must travel as an explicit RPC argument on every method — never via shared env. The vault repo enforces this via `messages_create(input, identity)` where `identity` is the caller's `{ package, environment, version_set_id }` resolved client-side from the caller's own env.
- **Alchemy's public `WorkerRef` factory drops the entrypoint field.** Workaround: construct the binding object directly with the internal `__entrypoint__` key — `bindings.GRANTS = { type: "service", service: pipelines_service, __entrypoint__: "PipelinesGrantsEndpoint" } as ReturnType<typeof WorkerRef>`. This is a known limitation of alchemy as of 0.93.x; when it ships the field publicly, swap back to the typed factory.
- **`CALLER_ENV` is the canonical key, NOT `CALLER_ENVIRONMENT`.** Each caller Worker reads its own stage from `env.CALLER_ENV` (defined per stage in its own infra/wrangler config). `caller-identity.ts:62` in pipelines maps stage values to two literals only: `staging` or `production`. The grants registry keys against these exact strings; anything else (e.g. `prod`, `live`, `preview`) won't match a grant and the call denies.

### Architecture rules

- **DO holds no business logic.** If you're writing transition logic inside `make_run_handler`, push it down into `@devpad/core/services/pipelines/runs.ts`.
- **State machine is pure.** `state-machine.ts` is deterministic — no clock, no random, no IO. Side effects belong in `runs.ts`.
- **Resolved rollout/gates JSON in `pipeline_run`** is the source of truth for in-flight runs, not the template files. Template edits don't affect running pipelines.
- **Forced-atomic gates fallback.** When the discriminator rewrites a declared `gradual` to `atomic` (DO migrations or unaffinitised assets), `resolve_run_plan` falls back to `defaultAtomicGates` since the declared gate map's transition keys no longer apply.

### Database

The pipelines module reuses the unified `Database` type — pipeline tables (`pipeline_*`) sit in the same D1 instance. Migrations land under `packages/schema/src/database/drizzle/` like everything else. The vault repo (`~/dev/vault`) does NOT bind to this D1; vault reaches grants exclusively through the pipelines `grants.check` RPC.

### Drizzle / D1 invariants (Phase 8)

- **RPC entrypoints that bind `env.DB` must wrap via `createD1Database(env.DB)` before passing to drizzle-typed services.** Raw `D1Database` bindings produce `db_error` at the first query because drizzle's typed accessor (`db.select()....`) expects the wrapped shape. The cached-wrap pattern lives in `grants-rpc-entrypoint.ts:35` — instantiate the wrapper once per entrypoint instance and reuse for subsequent calls.
- **Post-Phase 12/13.C the orchestrator is a singleton (`devpad-pipelines`) bound to `devpad-unified-db`.** Grants rows + run history live in production-only. The orchestrator's `--stage staging` path was removed in Phase 13.C — `packages/pipelines/infra.ts` hardcodes `devpad-unified-db` + `devpad-corpus` + `ENVIRONMENT: "production"`. A future canary deploy of the orchestrator would need re-introducing a stage discriminator.
- **Pipeline grants must exist BEFORE vault calls succeed.** Vault's grant check is fail-closed: if no `pipeline_grant` row matches `(package, environment, scope)`, the call denies with no escalation. Default seed for a new demo package is one row per stage: `(package, "staging", "anthropic:messages")` + `(package, "production", "anthropic:messages")`. The `environment` column only ever holds those two literals (matching `CALLER_ENV`'s two values) — `dev`, `preview`, etc. simply won't match.

### Drizzle-kit + manual migrations

If `drizzle-kit generate` auto-numbers a migration whose prefix collides with a manual migration not in `meta/_journal.json`, rename the generated SQL + snapshot to the next available index and add a matching journal entry. The journal advances monotonically; drizzle-kit's filename numbering is advisory. (We hit this with `0007_add_pulse_scope.sql` already on disk when generating `0008_pipelines.sql`.)

**Hand-written ALTER migrations don't generate paired snapshots.** When you add a column via a hand-written SQL migration (e.g. adding `window_ms` to `pipeline_analysis_template`), drizzle-kit doesn't auto-produce a paired entry in `meta/<n>_snapshot.json`. The migration still applies correctly at runtime since `_journal.json` is the source of truth — but the next time someone runs `drizzle-kit generate`, the snapshot may drift. Run `bunx drizzle-kit generate` after the next schema change to reconcile.

## Worker Architecture

- Routes NEVER read `c.env` -- all config comes from `c.get("config")` and `c.get("oauth_secrets")`
- `AppConfig` and `OAuthSecrets` types defined in `packages/worker/src/bindings.ts`

### Workspace dep declarations under bun's isolated linker (CRITICAL)

Bun 1.3+ installs with an isolated linker by default: a package can only resolve dependencies it explicitly declares in its own `package.json`. Transitive resolution through the workspace root does NOT happen at build time for bare specifiers.

- `packages/core/src/ui/styles/globals.css` does `@import "@f0rbit/ui/styles"`, so `packages/core/package.json` MUST declare `@f0rbit/ui` as a dependency. Without it, `node_modules/.bun/.../packages/core/node_modules/@f0rbit/ui` is not created and Vite/PostCSS fails with `ENOENT: ... open '@f0rbit/ui/styles'`.
- `apps/blog/src/middleware.ts` and `apps/media/src/middleware.ts` import `@devpad/core/ui/middleware`, so both apps' `package.json` MUST declare `@devpad/core` as a workspace dep. Without it, Rollup fails with `failed to resolve import "@devpad/core/ui/middleware"`.
- Rule of thumb: if a file uses a bare specifier (`@scope/pkg/path`), the package owning that file must declare the dep — even when the dep is already available transitively elsewhere in the workspace.

### @f0rbit/ui Utility Class Composition (CRITICAL)

Layout utilities use a **base + modifier** pattern. Modifiers only set CSS variables — they do NOT include `display: flex`. You MUST always include the base class:

- `.stack` = `display: flex; flex-direction: column; gap: var(--stack-gap, var(--space-md))`
- `.stack-sm` = MODIFIER ONLY, sets `--stack-gap: var(--space-sm)` — **must pair with `.stack`**

## AI Provenance & Protection System

### Entity Provenance

- `provenance()` schema helper adds `created_by` and `modified_by` columns (enum: "user" | "api", default "user") plus `protected` boolean (default false)
- `provenance()` → `entity()` → `owned_entity()` — adding columns to `provenance()` cascades to ALL entity tables
- Auth middleware sets `auth_channel` ("user" for session cookies, "api" for Bearer tokens) in Hono context
- All 4 upsert services (tasks, projects, milestones, goals) accept `auth_channel` and write it to `created_by`/`modified_by`
- Action table has a `channel` column recording which auth path created the action

### Protected Entity Policy

- Entities edited by a user (`auth_channel == "user"`) are auto-protected (`protected = true`)
- API-channel writes to a protected entity are rejected with 409 Conflict unless `force: true` is passed
- `force: true` clears the protection flag — the entity becomes unprotected again
- `ProtectedError` type and `isProtectedError()` guard in `packages/schema/src/errors.ts`
- `force` is a validation-only field — must be destructured out before DB write: `const { id, force: _force, ...fields } = data;`

## Cloudflare API Integration (Phase 6 — Workers Versions multipart upload)

## Pulse Integration

devpad federates with `@f0rbit/pulse` (analytics + observability, separate Cloudflare Worker; source: `~/dev/pulse`). The integration is server-to-server only — admin keys never reach the browser.

### Auth + scope

- `api_keys.scope` enum includes `"pulse"` (added in migration `0007_add_pulse_scope.sql`). Use this scope when issuing keys for analytics access; `"all"` is a superset.
- `AppVariables.api_key_scope` is `null` for cookie-auth (browser sessions) and a scope literal (`"pulse"`, `"all"`, etc.) for API-key auth. Routes that branch on scope must handle `null`.
- `getUserAndScopeByApiKey()` in `packages/core/src/auth/keys.ts` returns both user_id and scope; auth middleware exposes scope via `c.set("api_key_scope", ...)`.

### Worker proxy — `/v1/pulse/*`

- `packages/worker/src/routes/v1/pulse.ts` is a server-to-server forwarder. It holds `pulse_internal_key` (config-injected) and forwards to `pulse_api_base` after rewriting `/v1/pulse/<rest>` → `/<rest>`.
- Ownership enforcement is per-route via `doesUserOwnProject` from `packages/core/src/services/projects.ts`. Pulse trusts whatever devpad forwards — the boundary is here, not upstream.
- 60s edge cache on `GET /summary | /errors | /logs | /latency`. None on `/events` or `/admin/*`.
- Pulse-unreachable (fetch failure or network 502) maps to 503 with `{ error: "pulse_unreachable" }`. Treat 503 as "pulse not deployed yet," not as an error in dashboard pages.

### ApiClient — `client.pulse.*`

- `client.pulse.{summary, events, errors, logs, latency}` for reads, `client.pulse.subs.*` for subscription CRUD, `client.pulse.keys.*` for ingest-key issuance. All return `ApiResult<T>` (devpad's existing wrapper).
- All methods hit devpad's `/v1/pulse/*` proxy — they do NOT call pulse directly. Public site never sees pulse's URL or admin keys.
- **`client.pulse.{summary,errors,logs,latency,events}` are Zod-validated, not `unknown`.** Schemas live in `packages/schema/src/pulse/types.ts` (`PulseSummarySchema`, `PulseErrorsResultSchema`, `PulseLogsResultSchema`, `PulseLatencyResultSchema`, `PulseEventsPageSchema`), exported via `@devpad/schema/pulse` and re-exported from `@devpad/api`. They mirror pulse's real `Summary`/`ErrorsResult`/`LogsResult`/`LatencyResult`/`EventsPage` types in `~/dev/pulse/packages/core/src/query.ts` — there is no published pulse schema package to import from, so keep these in sync by hand when pulse's query shapes change. `PulseSummary` has `{pageviews, sessions, events_total, errors, request_count, p95_latency_ms, by_day}` — **not** an invented `{totals, series}` shape (that was the root cause of a bug where the dashboard showed "no analytics data yet" for every project regardless of real data). Use `pulseSummaryHasData(summary)` for the empty-state check.
- **Rebuild `@devpad/schema` then `@devpad/api` after editing pulse schemas or `packages/api/src/api-client.ts`.** `apps/main` consumes `dist/index.d.ts`, not source. Run `cd packages/schema && bun run build && cd ../api && bun run build` before typechecking dependent packages or you'll see stale type errors.

## Pipeline Run Semantics (Phase 9)

- Analysis gates fail OPEN: when `pipeline_analysis_template` row is missing for a gate's `template_id`, the evaluator returns `{ verdict: "Pass", reason: "no_template_configured" }` + emits a pulse `gate_analysis_no_template` event. To get fail-closed behaviour, populate a real template row. Implicit "default" template doesn't exist.
- `pipeline_run.kind` is `"deploy" | "rollback"`. Rollback runs are spawned by `POST /runs/:id/rollback` even from terminal states; they target the predecessor version-set via corpus lineage and use atomic shape + auto gate. They're separate run rows with their own audit trail.
- `wrangler d1 migrations apply` requires a user-level token with `User Details: Read`. The resource-scoped `CF_API_TOKEN` in `.env` (sized for Alchemy) lacks it — which is fine, because humans should never be applying migrations anyway (next bullet).
- **NEVER hand-apply a D1 migration — not even "just this once."** Migrations travel exactly one path: schema edit in `packages/schema/src/database/schema.ts` → `drizzle-kit generate` produces the SQL + paired snapshot + journal entry → commit → CI applies it via `wrangler d1 migrations apply` inside the `Deploy Staging`/`Deploy Production` workflows. Running `bunx wrangler d1 execute <db> --remote --file <migration>.sql` by hand applies the schema WITHOUT writing the `d1_migrations` row, so the next CI deploy retries the same migration and hard-fails with `duplicate column name` (SQLITE_ERROR 7500), blocking all subsequent deploys until repaired.
- **Drift-repair procedure (when the ban was violated anyway).** For each suspect migration, check whether its objects already exist remotely (`pragma_table_info('<table>')` for ADD COLUMN migrations, `sqlite_master` for CREATE TABLE/INDEX migrations) and compare against `SELECT name FROM d1_migrations ORDER BY id`. For every migration whose objects exist but whose row is missing: `INSERT INTO d1_migrations (name) VALUES ('<exact filename>')`. Leave genuinely-unapplied migrations unrecorded — CI applies them normally. Then rerun the failed workflow. (This exact drift shipped on 2026-08-22: staging + production both carried hand-applied 0012/0013.)

  - **Chaining `.then()`/`.catch()` directly onto `.json()` breaks sink detection** (`response.json().then(x => Schema.parse(x))`, `response.json().catch(() => null)`) — the `.json()` call's immediate AST parent becomes a `.then`/`.catch` `MemberExpression`, which the rule never recognizes as a sanctioned shape, regardless of what happens further down the chain. Fix: `await`-then-parse in the same expression (`Schema.parse(await response.json())`), or wrap in a real `try`/`catch` statement instead of promise chaining.
  - **A bare `x = JSON.parse(...)` reassignment to an already-declared variable is ALSO flagged**, even when `x` was pre-declared `let x: unknown;` — a plain `AssignmentExpression` is never a recognized consuming shape, regardless of the target's declared type. Fix: parse into a **fresh** `const`-declared, explicitly-`unknown`-annotated variable inside the block, then assign that variable's value to the outer one (`const parsed: unknown = JSON.parse(t); x = parsed;` — the second line is a plain identifier assignment, invisible to the rule).
  - **A `JSON.parse(...)` call nested inside a ternary is never sanctioned no matter what wraps the ternary** (`cond ? JSON.parse(x) : null` as a declarator initializer) — the rule only inspects ONE level of parent AST context, and `ConditionalExpression` isn't a recognized shape. Lift the call out into its own `if`/`else` first.

## CLI npm-bundle gotchas

- **`bun build --packages=bundle` inlines `__dirname` as a literal string when a bundled dependency reads it at its own module top level.** `blake3-wasm`'s node loader does `path.join(__dirname, "blake3_js_bg.wasm")` — once bundled, bun bakes in the _build machine's_ absolute path (e.g. the GitHub Actions runner's `/home/runner/work/...`), not a path resolvable on the eventual consumer's machine. ## v2.4 Graph (Phase A1)

- **Graph invariant rule**: every structural task mutation (reparent, blocks-edge insert, claim) is ONE SQL statement carrying its full invariant in the WHERE clause (recursive CTE guards inline, `packages/core/src/services/graph/graph.ts`). Validate-then-write sequences on tree structure are forbidden — D1's single-writer serialization is the only race protection we have. On a 0-row guard failure, read-only follow-up queries build a typed error (never re-attempt the write).
- **All graph mutations use `rev`-based OCC**; 409-shaped responses carry the current row (`{kind:"graph_conflict", current}`). New mutation endpoints/apply-ops must accept `base_rev` and never blind-write — this includes plain field updates, not just structural ones (A1.4's `apply_op` "update" carries `base_rev` for this reason, even though the original op-list sketch didn't call it out).
- **`packages/core/src/services/graph/atomic.ts`'s `run_atomic(db, fn)`** is the only sanctioned way to run a multi-statement graph mutation atomically. D1 has no interactive transactions (no raw BEGIN/COMMIT); bun-sqlite has real transactions but not D1's `.batch()` API. `run_atomic` wraps bun-sqlite in BEGIN/COMMIT/ROLLBACK (rolling back on both a `!ok` Result AND a thrown exception); on D1 it currently runs `fn` un-transacted — a known, documented limitation until a mutation path that needs D1 atomicity in production forces wiring the real `.batch()` array form.
- **Root `tsconfig.json` does NOT set `noUncheckedIndexedAccess`.** eslint's type-aware rules (`no-unnecessary-condition`, `no-non-null-assertion`-adjacent checks) use that root config, so `array[0]` and array destructuring are treated as non-optional throughout the whole repo's lint pass — even though `packages/api/tsconfig.json` sets it locally for its own `tsc` build. Don't defensively guard `rows[0]` after a `rows.length === N` check (oxlint/eslint will flag it as an unreachable/unnecessary conditional and `no-non-null-assertion` bans the `!` escape hatch too) — check `.length` and index directly, matching the existing convention in `tasks.ts`'s `upsertTask`.
- **Fractional rank keys** (`packages/core/src/services/graph/rank.ts`) are self-headed base-36 (`rank_between`) — never hand-construct a rank string; only `rank_between`'s output is valid. `""` (the schema default) is treated identically to `null`.

## v2.4 Graph (Phase A2)

- **Outbox rule**: every task/edge mutation writes its `task_event` row in the SAME `run_atomic` call as the state change, via `write_with_event` (`packages/core/src/services/graph/outbox.ts`). A mutation path without an event row is a bug, full stop — grep for `db.update(task)`/`db.insert(task)` outside `write_with_event`/the completion engine's `run_atomic` scope when reviewing a new mutation path.
- **`run_atomic` now uses a uniquely-named `SAVEPOINT` instead of bare `BEGIN`/`COMMIT`** (bun-sqlite path) — the outbox wiring makes `run_atomic` calls nest routinely (e.g. `apply()` wraps a batch of ops, several of which are themselves `set_parent`/`claim`/`add_link` calls that wrap their own write+event pair), and plain `BEGIN` cannot nest in SQLite while `SAVEPOINT` can. This is a strict superset of the old behavior — a top-level savepoint still behaves like a real transaction.
- **Bubbling test seam**: `CompletionEngine` consumers test against `InMemoryCompletionEngine` (`completion-memory.ts`); the SQL engine (`SqlCompletionEngine`, `completion.ts`) is ONLY tested against real SQLite (`create_test_db` — bun:sqlite + migration replay). The property suite (`bubbling-properties.test.ts`, seeded RNG via a hand-rolled `mulberry32` — pin the printed seed to reproduce a failure) gates any change to the cascade SQL; it must stay green before phase A3 work lands.
- **The cascade guard is one UPDATE per hop with all four predicates in its WHERE clause** (not-completed, `completion_policy='auto_children'`, `EXISTS` an alive child, `NOT EXISTS` an incomplete alive child) — never hoist any of these into application code. `completion.ts`'s `cascade_from` is exported specifically so the sweeper can re-run the identical cascade logic for crash repair rather than a parallel reimplementation; it's idempotent by construction (an already-COMPLETED parent short-circuits before any write).
- **Timestamp format inconsistency, easy to trip on**: the graph module's raw-SQL writes stamp `updated_at` via SQLite's native `CURRENT_TIMESTAMP` (`YYYY-MM-DD HH:MM:SS`, UTC, no `T`/`Z`/millis), but the older non-graph service layer (`tasks.ts`'s legacy fields, `goals.ts`, `milestones.ts`, etc.) stamps it via `Date.prototype.toISOString()` (`YYYY-MM-DDTHH:MM:SS.sssZ`). A string-comparison cutoff built with `toISOString()` against a graph-table timestamp compares as always-less-than (`' '` sorts below `'T'`) and silently matches nothing — this bit the sweeper's "recently completed" window (`sweeper.ts`'s `sqlite_utc_cutoff` helper does the correct conversion). Any future time-windowed query over `task`/`task_event` needs the same conversion, not `new Date(...).toISOString()` directly.
- **A deleted node's ancestor-refresh walk is a dead end by design**: `ancestors()`/`subtree()` (`graph.ts`) both stop walking at a deleted node (a deleted node's subtree is invisible to its own ancestors too), which means `refresh_rollup_chain(db, deleted_node_id)` refreshes that node's own row but returns zero ancestors to also refresh — correct, since nothing above a deleted node should count its subtree anymore. The flip side: a deleted node's OWN cached `task_rollup` row never gets a further refresh once something changes below it (nothing re-triggers it). This is harmless in practice (nothing displays a deleted task's ProgressRing) but is a real gap if some future consumer ever reads a deleted task's rollup directly — don't "fix" it by pointing `ancestors()` through deleted nodes, since that would break the intended visibility-cascade semantic instead.
- **No dedicated "delete task" mutation exists yet** — v2.4 has soft-delete as a schema column (`task.deleted`) but no route/service function that flips it (unlike `task_link`'s `remove_link`). Any future delete path MUST call `refresh_rollup_chain(db, parent_id)` in the same atomic write, matching every other structural mutation's rollup-maintenance obligation.
- **Known, accepted invariant-enforcement gap**: `tasks.ts`'s `upsertTask` (the legacy PATCH `/tasks` / `devpad_tasks_upsert` path) can change `parent_id` directly via a blind field update — it does NOT run through `set_parent`'s guarded cycle/depth-checked SQL. Rollup refresh is wired for this path (`upsertTask` detects a `parent_id` diff and refreshes both chains), but the cycle/depth invariant itself is only protected on the `set_parent`/reparent-op path. The A2.4 sweeper's structural-invariant verification (cycle-free + depth ≤ cap) is the backstop for this specific gap, not a redundant check.
- **`CompletionEngine`'s error types are split**: `CompleteError` (`ServiceError | GraphConflictError`) for `complete()`, `ReopenError` (adds `ReopenRejectedError`) for `reopen()` — don't reuse one union for both; `reopen_rejected` can never come out of `complete()`, and a shared type would let callers write dead-code branches undetected.
- **`POST /tasks/:id/done`** (`done_request: { base_rev }`) is the single completion entrypoint — `tasks.ts`'s `upsertTask`, `apply.ts`'s `complete` op, the MCP tool `devpad_tasks_done`, and the CLI's `tasks done <id>` all resolve to the same `SqlCompletionEngine.complete()` call. Response shape `{ completed, bubbled, hooks_fired }` — `bubbled` is the ordered ancestor chain a B2 ripple animation replays verbatim; `hooks_fired` stays an empty placeholder until phase A3 wires real dispatch. Any new completion-triggering surface must call this engine, never write `progress`/`completed_via` directly.
- **Known, disclosed limitation carried from A1**: `run_atomic` on D1 runs `fn` un-transacted — the guarded state UPDATEs are each individually atomic (single SQL statement), but a crash between the state write and its paired outbox-event write is only fully covered by the sweeper for the completion-cascade case specifically, not for every event kind (`task.updated`, `edge.created`, etc.) in production. This gap remains open on D1 as of phase A3 — phase A3's hook dispatch only fires for a `task_event` row that was successfully written, so a lost non-completion-kind event silently means a hook that never fires, with no compensating repair path (unlike the completion cascade, which the sweeper does repair).

## v2.4 Hooks (Phase A3)

- **Delivery guarantee, precisely**: given a `task_event` row IS durably written (see the D1 outbox-pairing gap above), hook delivery to a matching hook is at-least-once-attempted and exactly-once-in-effect. At-least-once because the post-commit drain middleware (`packages/worker/src/index.ts`) hands every `dispatch_status='pending'` row to the queue after each request, AND the 5-min cron's `drain_stale_events` re-enqueues anything still `pending` after 60s as a backstop for a dead `waitUntil`. Exactly-once-in-effect because `hook_delivery`'s PK (`hash(event_id, hook_id)`) makes replaying the same event/hook pair a no-op once it reaches a terminal state (`delivered`/`failed_permanent`). **Caveat**: the cron backstop only runs when `HOOKS_QUEUE` is bound (`drain_stale_events` no-ops otherwise) — until the ops prerequisite (`wrangler queues create devpad-hooks[-preview]`) is done, dispatch is best-effort-per-request only, with no cron safety net.
- **`hook_delivery.status='failed_permanent'` is the visible DLQ** — retention (`packages/core/src/services/hooks/retention.ts`) NEVER prunes it regardless of age. A transient failure is promoted to `failed_permanent` once it hits `HOOK_ACTION_MAX_TRANSIENT_ATTEMPTS` (`dispatch.ts`), independent of the underlying Cloudflare Queue's own `max_retries` — `wrangler.toml` deliberately has no `dead_letter_queue` configured, since a second queue+consumer would be extra ops surface for a guarantee the delivery ledger already provides at the app level.
- **`DispatchProvider` seam**: `CFQueueProvider` (real `HOOKS_QUEUE` binding) vs `InMemoryDispatcher` (runs the consumer synchronously). The bun dev/test path can NEVER see `c.env` (Hono's `app.fetch(request)` 2-arg form used by `dev.ts` leaves `c.env` `undefined`) — the dispatch provider is injected via `ApiOptions.dispatch` the same way `db`/`config` already are, never read from `c.env` on that path. Don't reintroduce a raw `c.env.HOOKS_QUEUE` read in code that also has to run under `dev.ts`.
- **Scoped-key guard applied to `tasks.ts`/`scanning.ts` in the SAME pass as the new `hooks.ts` route** (task A3.1), even though the adversary checklist's literal wording only calls out "new routes" — the guard needed a concrete existing resource type to prove itself against before hooks existed. `github.ts`'s inbound webhook route is deliberately UNGUARDED — it's unauthenticated by design (GitHub can't send devpad session/API-key auth); the HMAC signature is its only auth boundary.
- **Two identity generations for vault adapters** (see `~/dev/vault/AGENTS.md` for the vault-side detail): the original Anthropic adapter reads caller identity off vault's own env vars; the GitHub adapter (task A3.5) takes identity as an explicit second RPC argument instead, matching the documented cross-repo invariant that CF service bindings don't propagate caller env vars. Every future vault adapter call site in devpad should pass identity explicitly (see `packages/core/src/services/hooks/actions/vault.ts`).
- **Pipeline action executor has a known gap**: the real orchestrator's `POST /runs` also requires `version_set_id`, which a hook's `{kind: "pipeline", package_id}` action has no way to supply — firing it today gets a 400 from the orchestrator, correctly classified as a permanent failure (not a crash), until a follow-up adds a "run the package's latest version-set" convenience or extends the hook action shape.
- **No route exists yet to toggle `project.github_autoclose`** — task A3.6 added the schema column and the inbound webhook reads it, but there's no settings UI or API surface to flip it; it's DB-default `false` until a follow-up adds one.

## v2.4 Docs + Signoffs (Phase A4)

- **Marker payload is base64, not raw JSON** (`packages/core/src/services/docs/markers.ts`) — the plan's ideation sketch shows the JSON inline as comment text, but standard base64's alphabet (`A-Za-z0-9+/=`) never contains `--`, so a thread reply body with literal `--` (routine in code snippets) can never terminate the `<!-- devpad:thread:begin ... -->` comment early. The wire shape (paired comments carrying the full `ThreadMarker`, Zod-validated on read) is otherwise unchanged from the plan.
- **`sanitize_html` (task A4.1) strips ALL comments unconditionally, always** — including a forged `devpad:thread:*` marker an agent tries to smuggle in. This has a direct consequence for the annotation engine (task A4.2): `store.ts` splits into `push_document_raw` (pushes HTML as-is, no sanitize) and `push_document` (sanitize + delegate to raw). `threads.ts`'s `reconcile()` calls `sanitize_html` itself on the marker-STRIPPED content, then re-embeds markers into the now-clean text and pushes via `push_document_raw` — never `push_document`, which would immediately strip the markers it just added. `push_document_annotated` (in `threads.ts`) is the actual route-level entrypoint for every doc push (a no-op superset of plain sanitize for a marker-free doc); `store.push_document` remains for direct/internal callers that don't need annotation awareness.
- **`reconcile()` re-validates EVERY marker on every push, not just unpaired ones** — a still-paired marker whose bracketed content silently drifted from its stored quote (an agent edited the annotated text in place, markers intact) is re-verified against `resolve_anchor` too and orphans if the quote's gone, per architecture-decisions' "verifies-then-falls-back, always validated against the stored quote." Don't special-case "paired = trust the position."
- **`promote()` (`store.ts`) is zero-copy** — it mutates the EXISTING corpus version's metadata (`backend.metadata.get` → add tag → `backend.metadata.put`) to add an `"approved"` tag, never a new `data` write or a new version. `DocVersionInfo` carries `content_hash` specifically so `signoff.ts` can stamp a decision row with exactly what was approved without a second corpus round-trip.
- **Approval-kind (`kind:"approval"`) tasks are human-only completable at exactly two chokepoints**, not scattered checks: `graph/completion.ts`'s `complete_leaf` SQL gained `AND (kind != 'approval' OR ${actor} = 'user')` in its WHERE clause (the existing graph-invariant style — one statement carries the full invariant), which covers `/done`, `upsertTask`'s fresh-complete path, and `apply`'s `complete` op simultaneously since all three funnel through `SqlCompletionEngine.complete()`. `apply.ts`'s `create` op is a SEPARATE raw INSERT that never touches the engine — it has its own explicit guard (`insert_task_row` rejects `kind:"approval"` + `progress:"COMPLETED"` outright) against a pre-COMPLETED approval task sneaking in that way. Any FUTURE raw task-row write path needs the same two-chokepoint treatment, not just the engine guard.
- **`signoff.decision:"auto"` (task A4.4's Buf-style fast path) bypasses `decide_checkpoint` entirely** — `auto_approve()` inserts the signoff row directly with `created_by:"api"`, no approval task node is ever created for an additive diff against an approved base (nothing needs to block downstream work). `decide_checkpoint` stays human-only-by-construction (rejects api-channel up front) for every OTHER decision path; "auto" is deliberately the one signoff decision that never goes through it.
- **Interface-report content is HTML-ESCAPED on push, not run through the markup sanitizer** (`signoff.ts`'s `push_interface_report`) — declaration text isn't real markup (parsing `Array<string>` as HTML tags would mangle it), but it's still untrusted input reaching corpus storage, so `sanitize_text` (plain-text entity-escape) is the right tool: a literal `<script>` becomes inert `&lt;script&gt;`. Escaping happens SERVER-SIDE (the trust boundary — a caller can hit `POST /docs/interface` directly, skipping the CLI); the CLI's `check` verb replicates the identical escape before hashing locally (`compute_local_hash`) so it still matches what the server stored. `classify_diff` compares escaped-vs-escaped on both sides — escaping never touches line boundaries, so line-based diffing is unaffected.
- **`list_versions` (`store.ts`) walks `parents` pointers, never sorts by `created_at`** — two pushes in the same millisecond (routine in tests, possible in production) tie on timestamp but never on lineage. Don't "simplify" this back to a timestamp sort.
- **`request_checkpoint_request` carries `project_id` explicitly** — the `signoff` table has no `project_id` column of its own (a signoff's subject can be a doc, a stage, or a future pipeline gate, none of which are uniformly project-scoped), so the approval task node's project comes from the caller, not an inferred join. Routes needing to scope a signoff by ownership (`GET/POST /signoffs/:id...`) do it via the LINKED approval task's `project_id`, not the signoff row directly.

## v2.4 Review Surface (Phase B3)

- **`@f0rbit/ui`'s Button `primary` is an empty class modifier, not a filled style** — pair it with the intended styling rather than assuming the modifier supplies a filled background.
- **`instanceof HTMLElement` across an iframe boundary always fails because the iframe has a different realm** — use null checks instead.

- **CSS-exfil fix (task_04427077…): the sanitizer FILTERS `<style>` content, it doesn't strip the tag.** `sanitize.ts`'s `sanitize_style_blocks` regex-scrubs `@import` and neutralizes every `url(...)` (background/behavior/-moz-binding/@font-face src alike) inside `<style>` blocks post-hast-sanitize; non-url CSS (colors, layout) survives untouched. `reconcile_docs_css` (owner-scoped, mirrors `verify_fold`'s pattern) repairs already-stored docs via `devpad admin reconcile-docs-css` — it calls `sanitize_style_blocks` directly, NEVER the full `sanitize_html`, because that strips every comment unconditionally and would destroy live annotation markers on any doc it touched.
- **DocViewer renders through a dedicated `GET /docs/:id/render` route into `<iframe sandbox="allow-same-origin">`** — deliberately WITHOUT `allow-scripts`. This combination is load-bearing: `allow-same-origin` alone still gives the PARENT frame's own trusted JS a live, readable `contentDocument`/`contentWindow.getSelection()` (what AnnotationRail needs to build selections), while script execution is gated by `allow-scripts` alone, independent of same-origin access — so any `<script>`/event-handler that ever slipped past ingest sanitization stays completely inert. The render route's own CSP (`default-src 'none'`, no `connect-src`/`script-src`/`frame-src`) is the second independent layer.
- **`createResource` is unused everywhere else in this codebase and doesn't fire its fetcher reliably under this Astro+Solid hydration setup** — a real, reproducible bug hit while building `docs-tab.tsx`/`doc-viewer.tsx` (clicks landed, state never updated, no console error). Every component in this repo uses plain `createSignal` + an explicit `async function` triggered by `onMount`/an event handler (see `milestone-lens.tsx`'s `load()` pattern) — follow that, not `createResource`, for any future data-fetching Solid component here.
- **`<Show when={signal()}>` only reruns its callback on falsy→truthy transitions.** Selecting a SECOND, different item (e.g. a second document in `docs-tab.tsx`) without `keyed` leaves the child component's own once-initialized signals (like `DocViewer`'s `selectedVersion`) pointed at the FIRST item. Use `<Show when={signal()} keyed>` (child receives the plain value, not an accessor) whenever selecting a new value should fully dispose+remount the child.
- **Two independent signoff shapes gate different things — don't conflate them.** `subject_kind:"stage"` signoffs (plan/types checkpoints per `stage.ts`'s `missing_checkpoints`) gate a stage TRANSITION and are decided directly in the checkpoint card (`checkpoints.tsx`'s `useStageDecision`). `subject_kind:"doc_version"` signoffs (the design checkpoint) gate approval of a SPECIFIC document version and are decided through that document's own DocViewer verdict bar (`annotation-rail.tsx`). A checkpoint card for a doc-version checkpoint is a link/preview only — never a second decide UI for the same signoff.
- **New `GET /signoffs?subject_kind=&subject_id=&checkpoint=` (`pending_signoff_for`)** — "is there something pending to decide right now", distinct from `latest_decided_signoff` ("what was the last DECIDED one"). Needed once the UI had to show/hide a verdict bar or checkpoint decide box conditionally; didn't exist before B3 since nothing needed it.
- **Annotation creation and signoff decisions are gated to the document's HEAD version only** — both `create_thread` and `decide_checkpoint` operate against head server-side; the UI mirrors this by hiding AnnotationRail entirely (with a "switch to the latest version" note) whenever `selectedVersion() !== pulled().document.head_version`, rather than letting a stale-version anchor silently misalign against head content.
- **A checkpoint card must resolve "the doc for this task" by MOST RECENTLY UPDATED, never first-array-match.** A task can accumulate more than one doc of a kind (e.g. `push_interface_report` called repeatedly without `document_id` creates a fresh doc each time) — `checkpoints.tsx`'s `latest_doc_of_kind` sorts by `updated_at` descending. Caught by a real, reproducible e2e flake (test-run pollution surfaced a stale doc from an earlier attempt), not a hypothetical.
- **The breaking/additive classification a checkpoint card shows is a CLIENT-SIDE re-derivation of `classify_diff`'s exact definition** (`diffLines(older, newer).some(l => l.kind === "remove")` ⟺ breaking) — this is intentionally the same algorithm as `interface-report.ts`'s server-side one (a diff with zero removed lines is exactly the "old is a subsequence of new" additive case), not an approximation. It is NOT the authoritative signal used for gating (that's the server's own classification at push time, which isn't persisted for later display) — purely a display convenience.
- **`@devpad/api`'s public surface is a CURATED re-export list in `packages/api/src/index.ts`, not a wildcard `export *`.** A type declared `export type X` inside `api-client.ts` is NOT automatically part of the package's public API — tsup's dts bundler only promotes types that `index.ts` explicitly re-exports by name. Forgetting this step produces a confusing "Module has no exported member" error in CONSUMING code (apps/main) even though the type is right there in `api-client.ts` — always add a new externally-consumed type to both files, and `bun run build:api` before trusting `apps/main`'s typecheck.
- **Fixed a real security gap found while building the scoped-keys panel: `DELETE /keys/:id` had no ownership check at all** — `deleteApiKey` now scopes its `UPDATE` by `(id, user_id)`; a key belonging to someone else resolves to the same `not_found` a nonexistent id gets (never leaks which case it was).
- **Hook enable/disable is its own route (`PATCH /hooks/:id/enabled`, `set_hook_enabled`), never routed through `upsert_hook`.** `PublicHook.action` never carries a webhook's `secret` back out (write-only, redacted to `has_secret` on every read) — a toggle-only caller resubmitting the general upsert would silently wipe `secret_encrypted` the moment it omits a field it never had access to.
- **The pipelines e2e fixture (`tests/e2e/fixtures/pipelines.ts`) unconditionally deletes+reinserts the shared `test-user-e2e`/`test-session` rows on every `seed.ts` run.** Running e2e specs across multiple separate `npx playwright test` invocations without reseeding between them eventually leaves a stale/missing session (symptom: every route 401s, "waiting-on-you"/outline pages render empty) that looks like an auth bug but is a seed-hygiene one. **Always `TEST_ENV=local bun run tests/e2e/seed.ts` immediately before each standalone spec invocation**, not just once per session.
- **A pending signoff created by one spec file's test leaks into ANOTHER spec file's assertion in a full-suite run**, because `reviews_pending`/"Waiting on you" aggregates across the WHOLE shared `test-user-e2e` account, not per-project. `waiting-on-you.spec.ts`'s "collapses to nothing when nothing is pending" test failed this way when `annotations.spec.ts` left a `doc_version` checkpoint request undecided. Any NEW e2e test that calls `request_checkpoint`/`POST /signoffs` must decide it in a `try/finally` (see `annotations.spec.ts`'s `decideCheckpoint` helper) so a mid-test assertion failure (or a flaky retry) still cleans it up.
- **`page.waitForLoadState("networkidle")` after a `page.reload()` (not the first cold `page.goto()`) is flaky specifically because vite's HMR client keeps a persistent WebSocket open**, which can prevent the page from ever reading "idle". The fix used throughout B3's specs: `networkidle` after the FIRST cold navigation (compiling a heavy new island can genuinely take longer than a fixed sleep), but a click-with-retry (no `networkidle`) for any RELOAD later in the same test, since the island's JS is already in vite's dev cache by then.
- **The Astro dev toolbar removal (`document.querySelector("astro-dev-toolbar")?.remove()`, documented in B2) must be called immediately before EACH screenshot, not just once after the first `page.goto()`** — it reappears across subsequent client-side navigations within the same page session. A `page.on("load", ...)` handler alone was insufficient for B3's multi-shot script; an explicit `await page.evaluate(...)` call right before every `page.screenshot()` was the reliable fix.

**LOD design**: `CAMERA_LEVELS = ["map", "neighborhood", "node", "detail"]` (`LEVEL_SCALE` maps each to a fixed zoom scale). `canvas-surface.tsx` only swaps the `stableLevel` signal (what `CanvasNode` actually renders) once `camera.is_moving()` goes false — mid-animation LOD thrash is deliberately avoided. `CanvasNode` reads `props.level` to decide body content: `map` collapses to a dot (title shown only for `milestone`/`goal` fold kinds), `neighborhood` is icon-only, `node`/`detail` show the full card, `detail` additionally shows an (currently empty-shell) detail panel when selected.

**Culling design**: `build_spatial_index` buckets node rects into a uniform grid (cell size ≈2x node footprint) rebuilt only when layout changes; `visibleIds` (a memo over `transform()` + `viewportSize()`) queries it once per frame. Culled nodes stay MOUNTED and get `display:none` (tldraw-style — avoids mount/unmount churn), never removed from the DOM. `visibleIds()` is `null` (meaning "render everything") until the real viewport has been measured via `ResizeObserver` — don't assert a specific visible/hidden ratio before that fires; poll instead.

**Known interaction gotcha (found + fixed in P2.5)**: `on_pointer_down`'s early-return guard for "this is a click candidate, not a pan gesture" must also exclude the HUD toolbar (`.canvas-toolbar`), not just `[data-canvas-node]`. Without it, `setPointerCapture` (called on every non-excluded pointerdown to support drag-panning) re-targets the FOLLOWING pointerup at the outer viewport, and Chromium silently suppresses the synthesized `click` when its up-target differs from its down-target — every HUD zoom-level button click was a no-op with no console error. Any new toolbar/HUD control added to the canvas surface needs the same exclusion.

**Known reactivity gotcha (found + fixed in P2.5)**: never read a Solid signal via an imperative "get current value to recompute" call (e.g. `transform()` inside `apply_clamped`) from a module method that might be invoked SYNCHRONOUSLY from inside a caller's `createEffect` — Solid's dependency tracking is call-stack based, not lexical, so the read gets accidentally attributed as a dependency of the CALLER's effect. Since `clamp_transform` always returns a new object (even when numerically unchanged), every subsequent write re-triggers that same effect, which reclamps and writes again — a self-sustaining loop that eventually stack-overflows (`Maximum call stack size exceeded` inside Solid's `runUpdates`/`completeUpdates`). Fix: wrap the internal read in `untrack()` (`camera.ts`'s `set_content_bounds`/`set_viewport`). Any camera/store module exposing imperative setters that read their own signals internally needs the same treatment if callers might invoke them from inside an effect.

**Workspace-dist-rebuild gotcha**: after pulling/rebasing canvas work (or any change touching `@devpad/schema`/`@devpad/api` types consumed by `apps/main`), rebuild both dists before running e2e or typecheck — `bun run --filter=@devpad/schema build && bun run --filter=@devpad/api build`. Stale `dist/` output silently masks type errors and can make fixtures import outdated schema shapes.

**E2E fixture**: `tests/e2e/fixtures/canvas.ts` seeds a dedicated `e2e-canvas-project` with the SAME `build_synthetic_graph(500)` generator the spatial-index unit test uses (single source of truth for the stress shape), remapping `project_id`/`owner_id` onto the seeded E2E user and batching inserts (100/chunk — bun:sqlite chokes on one 500-row insert). Cleanup keys off the `synthetic-` id prefix. See `canvas-core.spec.ts` for zoom/culling/keyboard/pan coverage; it's serial-mode across the whole file (same cold-hydration + CPU-contention rationale as `outline-interactions.spec.ts`/`lens-graph.spec.ts`) and uses a `clickLevel` retry helper for the same cold `client:load` hydration race those specs already document.

**Lint note**: `apps/main/src/components/solid/canvas/camera.ts` had a pre-existing `unicorn/no-array-sort` oxlint error (`Array#sort()` mutating `[...CAMERA_LEVELS]`) that was BLOCKING `bun run lint`'s `oxlint && eslint` chain before it ever reached eslint — fixed via `Array#toSorted()`. Fixing it unmasked a pre-existing, repo-wide ESLint backlog (28 errors across ~20 files, none in the canvas directory's OWN newly-added P2.5 code — confirmed identical error content/line-shift on a clean `git stash` diff) that `bun run gate` had never actually surfaced before on this branch. This is a real gap worth a dedicated cleanup phase; it is NOT part of P2.5's scope and was not fixed here beyond the one-line unblock.

### Canvas P3 — projections, placement, semantic travel

- **View-state storage**: `project_view_state` (D1, migration `0022_project_view_state`) is a PROJECTION over the graph — `layout: { pins: Record<task_id, {x,y}> }` only, never task fields. Last-write-wins, no history. Service in `packages/core/src/services/graph/view-state.ts`; routes `GET/PUT /v1/projects/:id/view-state`; client `client.projects.{getViewState,putViewState}`.
- **Placement**: `layout.ts`'s `apply_view_overrides(layout, node_size?, pins?)` applies pins (last-write-wins over dagre) AND, for any UNPINNED agent-created task (`created_by === "api"`), places it beside its PARENT's _resolved_ (pin-aware) position — pinning a parent drags its unpinned agent-created children along with it. Returns `programmaticIds` for the one-time placement-cue flash (`.canvas-node-cue`, fired once per session the instant the camera first leaves `map`).
- **Drag-to-pin**: `canvas-surface.tsx` distinguishes drag from click via a 4px pointerdown-then-move threshold, using its OWN `window`-level pointermove/pointerup listeners (added on node pointerdown) — deliberately NOT the viewport's pan pointer-capture, so drag and pan never fight. The drag's pointerup swallows the NEXT `onSelect` call for that node id (so a drag never also double-counts as a click-to-select) — this means a click immediately after a drag is a no-op; a REAL select needs a second click.
- **Pointer-capture gotcha extends to every new HUD/overlay control, not just `.canvas-toolbar`**: the P2.5 gotcha above (`setPointerCapture` re-targeting a control's pointerup, Chromium eating the synthesized click) bit the P3.3 reset-layout button too — it lives in `.canvas-layout-status`, a SEPARATE overlay div from `.canvas-toolbar`, so it needed its own entry in `on_pointer_down`'s exclusion selector (`[data-canvas-node], .canvas-toolbar, .canvas-layout-status`). Any future overlay control needs the same.
- **SSR crash gotcha**: an `onCleanup` that unconditionally references `window` (e.g. `window.removeEventListener(...)`) crashes Astro's server-render pass, which disposes the Solid root on the SERVER where `window` doesn't exist — guard with `typeof window !== "undefined"` in any cleanup that isn't itself gated behind a browser-only event having fired first.
- **Semantic travel** (Enter/dblclick) reuses `client.tasks.ancestors(id)` — the SAME primitive the outline's breadcrumb uses — rather than the outline's bounded `tree()` fetch: the canvas already holds the whole project graph (up to `PROJECT_GRAPH_TASK_CAP`), so travel only needs to swap the ancestor chain + move the camera, never re-fetch node data.
- **Lazy projections** (`projections.ts`): `fetch_node_projections` batches THREE existing project-scoped reads (`reviews.pending`, `docs.list({project_id})`, `pulse.summary`) ONCE when the camera first reaches `node`/`detail` LOD — never per-node, never re-fetched on subsequent LOD changes within the same graph load. `waiting`/`docsStatus` are exact matches; `pulseSpark` is a deliberate simplification — there's no per-task pulse metric binding yet, so it renders the project's OWN `by_day` series for any task carrying an outgoing `tracks_metric` link (the link's `ref` column is already shaped for a real per-task binding — a follow-up, not new backend work this phase).
- **E2E fixture note**: P3's tests use a dedicated tiny fixture (`e2e-canvas-p3-project`, `tests/e2e/fixtures/canvas-p3.ts`) rather than `E2E_OUTLINE_PROJECT_ID` — that fixture's graph spans many disconnected clusters wide enough that `camera.fit()`'s best-fit-of-4-discrete-levels can leave individual tasks culled off-screen at load, which breaks any test needing a real on-screen bounding box (e.g. a drag). Any future canvas test needing deterministic node positions should use (or extend) `canvas-p3`, not `outline`.
- **E2E camera-settle gotcha**: `.canvas-world`'s CSS `transition: transform 210ms` means a level's `data-lod` attribute flips at animation START, not end — any test code reading on-screen POSITIONS (a `boundingBox()` for a drag, not just presence/attribute checks) must wait out the tween too (`canvas-projections.spec.ts`'s `clickLevel` bakes in a ~300ms settle wait after every level change for this reason).

### Canvas P4 — IA absorption, mobile split, craft pass

- **IA before/after**: tabs go `overview · work · docs · pulse · pipeline · blog · settings · history` (8) -> `docs · pulse · pipeline · blog · settings · history` (6). Canvas is now the project home at `/project/:id` itself — it never gets its own tab entry (same as `overview` never did); the project title in `ProjectLayout.astro` links back to it. `overview.astro` (new, defensive — no such route ever literally existed, `overview` was always the content AT `/project/:id`), `work.astro`, and `canvas.astro` all 301 to `/project/:id`, preserving `Astro.url.search`, per the same B1 redirect pattern (`goals.astro`/`tasks/index.astro` were repointed to redirect straight to the final destination instead of chaining through the old `/work` hop).
- **The outline isn't gone — it's a `?view=list` mode of the SAME route, not a separate surface.** The canvas doesn't replicate the outline's row-level interactions (rename, edge-summary chips, milestone lens, keyboard-driven zoom breadcrumbs), so deleting `/work` outright would have been a real feature loss, not just an IA change. `index.astro` decides `want_outline = is_mobile || (view_param ? view_param === "list" : cookie_view === "list")` and branches its ENTIRE data-fetch + render between `loadOutline(...)` and `client.projects.graph(...)` — never fetches or renders both. A `?node=` deep link into a zoomed outline subtree survives the `/work` redirect (`work.astro` appends `&view=list` to the existing search rather than replacing it). A visible `.canvas-view-toggle` segmented control (plain SSR `<a>`s at the same visual weight as `.canvas-zoom-hud`, NOT the `@f0rbit/ui` `Tabs` component — that one is client-JS panel-switching, wrong tool for a control that swaps which SERVER-rendered surface loads) replaced a low-weight text link; picking either option writes a `canvas_view` cookie so a list-first user re-lands on the outline by default, but an explicit `?view=` in the URL always overrides the cookie.
- **Mobile is a UA sniff at SSR time, not a client-side viewport check** (`utils/is-mobile-user-agent.ts`). A resize-based check can't gate which island's `<script>` tag Astro emits — that decision has to be made before the response is serialized, and Astro only emits an island's hydration bundle for islands actually invoked in that request's render. Verified empirically (not just visually): a Playwright run with a mobile UA + 360px viewport recorded zero network requests matching `canvas-surface` after the outline branch rendered. Known tradeoff, accepted: resizing a desktop window below 720px doesn't retroactively swap to the outline (unlike the outline's own pure-CSS `≤720px` reflow) — a real mobile device's UA is the case this needs to cover, not a resized desktop browser.
- **Overview's content (description/status/visibility/repo link) moved into a `.canvas-home-hud` strip above the canvas surface**, not into the canvas node/detail panel — it's project-level metadata, not task-level, so it doesn't belong on any node. The pulse widget stays below the surface, unchanged.
- **`/canvas` now redirects before the canvas island hydrates**, which added enough latency to occasionally push `canvas-projections.spec.ts`'s FIRST navigation in the file past a bare default-timeout `toBeVisible()` — bumped that one assertion's timeout to `10_000` to match the node-visibility check already in the same helper. (One occurrence of this looked at first like a real regression but was actually the ALREADY-DOCUMENTED seed-hygiene gotcha above — `AUTHENTICATION_ERROR` on the redirected page after several standalone `bunx playwright test <file>` invocations without reseeding in between. Reseeding fixed it; the timeout bump was the one genuine, small regression from adding the redirect.)
- **Emoji-chip retirement**: the outline's `⛓`/`⚡` blocked/hook chips (raw emoji text) became lucide `Link2`/`Zap` icons, matching the icon-chip treatment the canvas node already used for stage/waiting/docs/pin/agent chips. `auto ⚙` and the `✓`/`✗` glyphs elsewhere were deliberately left alone — plain text/symbol characters, not colour emoji, used consistently as compact inline status marks — narrower scope than a full "no emoji anywhere" sweep.
- **`canvas-projections.spec.ts` graduated into `e2e:ci`** after two consecutive clean local runs post-fix (previously only `canvas-core.spec.ts` was in the CI subset).

### Canvas — hierarchy edges + fit-to-forest map level

- **`layout_graph` now feeds dagre a "hierarchy" edge (parent -> child) for every task with an in-project `parent_id`, before overlaying `task_link` edges** — without this, a project with real structure (goals -> milestones -> tasks) but few/no `task_link` rows renders as disconnected islands dagre ranks arbitrarily (confirmed on staging: 55 tasks, 5 `task_link` rows, "I don't see any connections between any of them"). `EdgeKind = TaskLink["kind"] | "hierarchy"` — hierarchy is structural (from `parent_id`), never a `task_link` row, and renders arrowhead-free/thin/muted (`canvas-edge-hierarchy`) since it's containment, not a directional relationship. The dagre graph is now `{ multigraph: true }` (a hierarchy edge and a `task_link` edge CAN share the same node pair — the old single-edge graph would silently drop one) with `acyclicer: "greedy"` as a defensive no-op (cycles are impossible via `parent_id`, guarded elsewhere).
- **`camera.ts`'s `map` level is no longer a fixed `0.58` scale — it's computed per camera instance as "fit ALL content in the viewport", capped at `neighborhood`'s scale** (so a tiny project's map tier never gets blown up past its next tier). Recomputed on every `set_content_bounds`/`set_viewport` call via an internal `map_scale` signal; `nearest_level`/`best_fit_level`/`zoom_to`/`fit()`/the wheel min-scale clamp all read it through a `level_scale(level)` closure instead of the static `LEVEL_SCALE` record for the `"map"` case specifically. `LEVEL_SCALE.map` (0.58) is now only the pre-bounds/viewport DEFAULT. **Any e2e test that assumed a fixed map scale (e.g. hardcoded wheel-delta math to hit "0.58 -> 0.82") needs to read the live scale off `.canvas-world`'s style instead** — see `canvas-core.spec.ts`'s `readWorldScale`. Similarly, a culling test that zoomed to `map` to prove offscreen nodes get hidden no longer works — `map` is BY DESIGN the "everything visible" tier now, so that kind of test needs a fixed-scale tier (`detail`) instead.

# Debugging

When running integration tests, logs will get piped to `packages/worker/server.log`, only read the logs if you're looking for errors.

In the case where you want logs in stdout, specify the exact test suite you want to run in the command using bun specifically rather than `make integration` & pass `DEBUG_LOGGING="true"` as an env variable to the function.
