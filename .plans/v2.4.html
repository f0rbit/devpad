Plan: devpad v2.4 — graph-based task rework

B3 in review — all else shipped

Rework devpad's flat task model into a graph-native, agent-first system: single-parent hierarchy with fractional ordering and optimistic concurrency, one typed edge table, edge-triggered completion bubbling via guarded conditional UPDATEs, a transactional-outbox → queue → hooks automation spine, a corpus-backed docs/annotation/sign-off loop, and finally the milestone/goal fold — then an outline-first UI arc over the proven backend. Two arcs, eight sequential phases, one PR each (A3 additionally ships a companion PR in ~/dev/vault). All six architecture decisions were locked during ideation (originally codenamed "Ripple"; the feature is v2.4 everywhere); this plan executes them and closes the ten identified gaps. Backend phases are TDD-first; UI starts only after the fold migration is verified.

Root cause

Stated goal: implement the decided v2.4 architecture — task graph, bubbling, hooks, docs/sign-off, milestone fold, outline UI.

Underlying need: devpad must become the coordination substrate for agent-driven development. Agents need one ready query, atomic claims, typed relationships, and completion signals that mechanically trigger automation (release-cutting, pipeline runs); the human's job must shrink to latency-critical sign-off on plans, types, and designs — never function bodies, never task bookkeeping. Today tasks have no relationships at all, mutations emit no events, and review happens out-of-band.

Why this matters: bolting parent_id onto the current model without the event/hook/sign-off spine would demand a second schema rework the moment automation arrives — the graph (blocks edges gate READY), the events (node.children_all_done), and approvals (approval nodes gating via blocks edges) share one vocabulary and must be co-designed. Conversely, shipping UI before the fold migration would build the outline against a schema that phase A5 immediately invalidates. Hence: backend arc first, migration last-in-arc, UI strictly after.

Alternatives considered

The six load-bearing decisions are locked (ideation synthesis, 2026-08-24 — see scratchpad/devpad-ripple.html §05) and are NOT re-litigated here: (1) graph on task now with milestone/goal fold as the final backend phase; (2) edge-triggered bubbling via guarded conditional UPDATE, sticky + stale badge + policy-only reopen, cron sweeper; (3) devpad-native automation spine — transactional outbox → dedicated devpad-hooks queue → pulse mirror (observability only) + hook registry with delivery ledger; (4) annotations stored as markers-in-doc over corpus versions (the user's explicit call); (5) generalized signoff table + kind:"approval" node projection, human-only completable; (6) SDLC v1 = stage enum + checkpoint-gated stepper with audited override, IA = "Waiting on you" atop /todo, net −1 nav tab. This section scores only the three choices that remained genuinely open inside that shape.

Open choice A: fractional rank encoding

A1: Hand-rolled lexicographic midpoint keys (base-36)

recommended

A ~50-LOC pure module rank_between(a: string | null, b: string | null): string generating base-36 strings that sort lexicographically, appending a mid-digit when neighbors are adjacent. Copy the reference algorithm from the fractional-indexing literature; own the code, property-test it.

Real-world examples

  • Figma — fractional indexing for multiplayer object ordering; chosen because concurrent inserts never conflict and order is a property of the row, not its neighbors. source
  • rocicorp/fractional-indexing — the reference implementation of the same algorithm (used across the Replicache/Reflect ecosystem); its README documents the exact edge cases the property suite must cover. source

Pros

  • Merge-safe for parallel agents by construction — two agents inserting between the same neighbors produce distinct, both-valid keys; no renumber transaction ever races the OCC rev guard.
  • Pure function → trivially unit- and property-testable per testing-strategy; ORDER BY rank is a plain indexed sort in D1.
  • No new dependency in the worker bundle; the A2 sweeper can rebalance pathologically long keys as routine maintenance.

Cons

  • Adversarial insert patterns (always-insert-first) grow key length linearly until the sweeper rebalances — accepted, sweeper task covers it.
  • We own the edge cases the npm lib already fixed — mitigated by porting its test vectors into our suite.

A3: Integer gap ranking (position × 1024, renumber on collision)

Real-world examples

  • Smallest storage; integer compare is the cheapest sort.

Open choice B: compat mechanics for the milestone/goal fold (phase A5)

B1: Service-level compat projections (TypeScript, old tables frozen)

recommended

Rewrite milestones.ts/goals.ts services to read/write task rows with kind ∈ {milestone, goal}, preserving the existing Milestone/Goal API shapes exactly (including after_id, computed from rank ordering). Old tables are frozen (writes removed), kept for dual-read verification, dropped in a later cleanup.

Real-world examples

  • GitHub sub-issues / issue types rollout — new hierarchy tables shipped while the existing REST milestone/issue contracts kept serving unchanged shapes projected from the new model. source

  • The compat layer is typed TS in the services layer — the existing integration suites (tests/integration/milestones-goals.test.ts et al.) pass unchanged and become the compat proof, for free.

Cons

  • after_id emulation from rank neighbors is mildly awkward (computed per list read) — bounded by milestone counts (small).
  • Direct-DB consumers of the old tables (none known beyond devpad itself) get a frozen snapshot, not live data — called out under Breaking.

Open choice C: annotation marker placement inside the doc

Locked decision 3 fixes storage (markers-in-doc, corpus versions as thread history). The remaining open axis is where the marker sits. Only three genuinely distinct placements exist — DB-rows-as-truth was already rejected by the locked decision, so no fourth option is fabricated.

C1: Inline paired range markers at the anchor site

recommended

<!-- devpad:thread:begin {json} --> … <!-- devpad:thread:end id --> wrapping the annotated span, with the W3C trifecta (quote + ~32-char prefix/suffix + char offsets) carried redundantly in the begin-marker JSON.

Real-world examples

  • OOXML (Word) tracked comments — w:commentRangeStart/w:commentRangeEnd markers inline in the document XML; comments survive edits because the range travels with content. source
  • CriticMarkup — inline annotation syntax embedded in plain-text docs, designed exactly for author⇄editor round-trips through dumb text tools (here: the agent). source

Pros

  • The marker travels with surrounding content when the agent edits the doc — position stays correct without re-anchoring in the common case; the trifecta is the fallback, not the primary mechanism.
  • The agent sees the thread in context on plans pull — the whole point of markers-in-doc; an appendix loses that locality.

Cons

  • Agent edits can orphan an end-marker (split pair) — the parser must treat an unpaired begin as a point annotation and flag it, feeding the orphan-don't-drop path.
  • DocViewer/sanitizer must strip marker comments before render (comments are inert HTML, but leaking them to viewers is noise).

Structural race serialization argument (gap 3)

Per-row rev OCC cannot protect tree-level invariants (two concurrent reparents jointly creating a cycle). The design rule: every structural mutation is ONE SQL statement whose WHERE clause carries the full invariant — reparent is a conditional UPDATE with a recursive-CTE ancestor check (WITH RECURSIVE anc AS (…) UPDATE task SET parent_id=… WHERE id=… AND rev=… AND NOT EXISTS (SELECT 1 FROM anc WHERE id=:new_parent) AND (depth check)); blocks-edge insert is INSERT … SELECT … WHERE NOT EXISTS (cycle CTE over blocks edges). D1's single-writer SQLite core serializes statements, so the invariant is evaluated atomically inside the write — there is no validate-then-write window. The A2 sweeper re-verifies invariants (cycle-free, depth ≤ 8, rollup consistency) on cron as the crash/bug backstop, never as the primary mechanism. SQLite supports CTEs on UPDATE/INSERT since 3.8.3; D1 qualifies.

Bubbling test seam (gap 9)

The load-bearing logic is guarded SQL that an in-memory fake cannot faithfully reproduce, so the seam is split: (a) CompletionEngine is an interface — SqlCompletionEngine (production, the guarded cascade) and InMemoryCompletionEngine (a ~40-LOC recording fake) — consumers (routes, hooks dispatch, UI-facing services) test against the fake; (b) the engine ITSELF is tested only against real SQLite via createBunDatabase + migration replay (same SQLite dialect as D1 — the SQL is identical); (c) concurrency is modeled by randomized operation-order permutations: because each cascade step is a single conditional UPDATE, atomic under SQLite's serialized writer, order permutation over a single connection is the honest local model of D1's single-writer interleaving. The property suite (A2.5) runs seeded random trees through randomized completion/reparent/reopen interleavings asserting: vacuous zero-children never fires; exactly one sibling triggers the parent; sticky semantics hold; cycle/depth guards hold; sweeper converges to invariant-clean state from injected mid-cascade crashes; rollup equals brute-force recount. Phase A3 (hooks) MUST NOT start until this suite is green.

Atomic write helper (D1 has no interactive transactions)

Every mutation must write state + outbox row atomically. D1 offers db.batch(); bun-sqlite (dev/test) doesn't share that API surface uniformly. A single helper run_atomic(db, statements) in the graph service wraps: D1 → batch(); bun-sqlite → sequential execution inside a BEGIN/COMMIT. All v2.4 mutation paths go through it; hand-rolled multi-statement writes outside the helper are an adversary-checklist violation in every backend phase.

AGENTS.md updates

Patterns for the coder to write into /Users/tom/dev/devpad/AGENTS.md at each phase close (this section is the audit trail; entries land under a new "v2.4 graph" heading).

  • (A1) Graph invariant rule: every structural task mutation (reparent, blocks-edge insert, claim) is ONE SQL statement carrying its full invariant in the WHERE clause (recursive CTE guards inline). Validate-then-write sequences on tree structure are forbidden — D1's single-writer serialization is the only race protection we have.
  • (A1) All graph mutations use rev-based OCC; 409 responses carry the current row. New mutation endpoints must accept base_rev and never blind-write.
  • (A2) Outbox rule: every task/edge mutation writes its task_event row in the SAME run_atomic call as the state change (packages/core/src/services/graph/atomic.ts — D1 batch / bun-sqlite transaction). A mutation path without an event row is a bug, full stop.
  • (A2) Bubbling test seam: CompletionEngine consumers test against InMemoryCompletionEngine; the SQL engine itself is ONLY tested against real SQLite (createBunDatabase + migration replay). The property suite (bubbling-properties.test.ts, seeded RNG — pin the printed seed to reproduce) gates any change to the cascade SQL.
  • (A3) Hooks infra: queues are devpad-hooks (prod) / devpad-hooks-preview (preview); local dev + tests use InMemoryDispatcher (synchronous consumer). Delivery idempotency is the hook_delivery PK (hash(event_id+hook_id)) — never add application-level dedup on top. failed_permanent rows are the DLQ and are never auto-pruned.
  • (A3) devpad's vault caller identity is {package_id:"devpad", environment: production|staging} (preview→staging); grants are per-repo github:releases:<repo> rows, fail-closed. Webhook secrets are ENCRYPTION_KEY-encrypted (raw needed for HMAC) — never hashed, never logged.
  • (A4) Doc safety: sanitize-on-push means corpus only ever stores safe HTML; every write path into the docs store (push, thread mutations, orphan moves) goes through sanitize.ts. Render routes add CSP as defense-in-depth. Markers are paired devpad:thread HTML comments with Zod-parsed JSON — treat unparseable markers as orphans, never drop them.
  • (A4) Approval-kind tasks are human-only: any api-channel mutation 403s via the auth_channel guard in the tasks service — this rides provenance, don't re-implement it per-route.
